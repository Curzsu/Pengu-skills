# 已知串联链弹药库

收录后端高频考点的"已知串联链"。建网前先扫对应条目，已有串联链直接复用，避免每次从零想。

格式：每条按"向下（原理层）/向上（演进层）/横向（对比层）"三个方向组织，写清每步为什么能推过去。

## 并发锁

### synchronized 锁升级

**向下（原理层）**：
synchronized 重量级锁 -> OS mutex 原语（因为 JVM 用操作系统互斥量实现重量级锁）-> 用户态/内核态切换（mutex 涉及线程挂起/唤醒，需要内核态）-> Java 一对一多线程模型（Java 线程直接映射 OS 线程，所以内核态切换逃不掉）

**向上（演进层）**：
早期 synchronized（JDK 1.6 前，上来就重量级锁）-> JDK 6 锁升级优化（偏向锁+轻量级锁+自适应自旋，减少内核态切换）-> JDK 15 废弃偏向锁（JEP 374，现代硬件 CAS 便宜了，偏向锁维护成本不划算）-> Java 21 虚拟线程（协程，用户态调度，绕开 OS 线程一对一映射）

**横向（对比层）**：
synchronized（JVM 内置，锁升级优化）vs ReentrantLock（AQS 实现，可公平/可中断/tryLock）vs 乐观锁 CAS（无锁，适合低竞争）

### volatile

**向下（原理层）**：
volatile -> 内存屏障（LoadLoad/StoreStore/LoadStore/StoreLoad）-> JMM（Java 内存模型，主存+工作内存）-> CPU 缓存一致性协议（MESI）-> 缓存行/伪共享

**向上（演进层）**：
单核时代的可见性不是问题 -> 多核 CPU 普及，每个核有 L1/L2 缓存 -> JMM 抽象化内存可见性问题 -> volatile/happens-before 规范化

**横向（对比层）**：
volatile（可见性+禁止指令重排，不保证原子性）vs synchronized（可见性+原子性+互斥）vs Atomic 类（CAS 保证原子性）

### AQS

**向下（原理层）**：
AQS -> state 变量（volatile int）+ CLH 双向队列 -> CAS 修改 state -> LockSupport.park/unpark（线程阻塞/唤醒）-> Unsafe.park（native，OS 级别线程挂起）

**向上（演进层）**：
ReentrantLock/ReentrantReadWriteLock/CountDownLatch/Semaphore/TimedLock（都基于 AQS）-> StampedLock（JDK 8，乐观读，不基于 AQS）

**横向（对比层）**：
AQS（独占+共享双模式，模板方法）vs synchronized（JVM 内置，无队列可见性）vs LongAdder（分段思想，低竞争场景）

## 数据库

### MySQL 索引

**向下（原理层）**：
B+ 树索引 -> B+ 树结构（叶子节点链表，非叶子只存索引）-> 为什么不用 B 树（B+ 树叶子链表支持范围查询，非叶子不存数据，单节点能存更多索引，树更矮）-> 为什么不用哈希（哈希不支持范围查询）-> 磁盘 IO（B+ 树高度低=IO 次数少）

**向上（演进层）**：
单列索引 -> 联合索引（最左前缀原则）-> 覆盖索引（索引覆盖查询字段，免回表）-> 索引下推（ICD，5.6，在存储引擎层过滤）

**横向（对比层）**：
聚簇索引（数据和索引一起，InnoDB 主键）vs 非聚簇索引（数据和索引分开，MyISAM）-> 二级索引回表

### MySQL 事务隔离

**向下（原理层）**：
事务隔离级别 -> MVCC（多版本并发控制）-> undo log（版本链）+ read view（快照）-> RC 每次 select 生成新 read view / RR 事务开始生成一次 -> 间隙锁/临键锁（解决 RR 下的幻读）

**向上（演进层）**：
读未提交 -> 读已提交（RC）-> 可重复读（RR，MySQL 默认）-> 串行化（解决所有问题但性能差）

**横向（对比层）**：
MVCC（快照读，无锁）vs 当前读（加锁读，select for update / lock in share mode）

## 缓存

### Redis 持久化

**向下（原理层）**：
RDB（内存快照）-> fork 子进程 + COW（copy-on-write）-> 全量备份
AOF（命令日志）-> 追加写入 -> AOF rewrite（重写压缩）-> fsync 策略（always/everysec/no）

**向上（演进层）**：
纯内存（重启丢数据）-> RDB（定期快照，恢复快但可能丢数据）-> AOF（命令日志，丢得少但恢复慢）-> RDB+AOF 混合（4.0+）

**横向（对比层）**：
RDB（全量、二进制、恢复快、可能丢）vs AOF（增量、文本、恢复慢、丢得少）

### 缓存一致性

**向下（原理层）**：
缓存一致性 -> 缓存击穿/穿透/雪崩 -> 布隆过滤器（防穿透）-> 互斥锁/逻辑过期（防击穿）-> 随机过期时间（防雪崩）

**向上（演进层）**：
Cache Aside（先更库再删缓存）-> 延迟双删（删缓存->更库->延迟再删）-> 消息队列保证最终一致

**横向（对比层）**：
先删缓存再更库（并发下会脏读）vs 先更库再删缓存（并发下也可能脏读，但概率低）vs 消息队列（强一致但复杂）

### Redis 为什么快

**向下（原理层）**：
内存存储（纳秒访问，比磁盘快 10 万倍，砍磁盘 IO 瓶颈）+ 单线程执行命令（无锁竞争、无上下文切换，砍锁瓶颈）+ IO 多路复用 epoll（红黑树管 fd + 就绪链表 O(1) 取事件，让单线程能同时处理几万连接，是单线程能高并发的关键）+ 专用数据结构（SDS O(1) 取长/ziplist 紧凑存储/skiplist O(logN) 范围查询，砍通用结构开销）。四者配套缺一不可：单线程本身不能并发，是 epoll 让它扛住并发。

**向上（演进层）**：
早期 Redis（单线程 + epoll，单核够用）-> 多核 CPU 普及，单线程只用一核成瓶颈 -> Redis 6.0 引入多线程网络 IO（协议解析、回写 socket 多线程，命令执行仍单线程保持无锁）-> 为什么不彻底多线程执行命令：多线程改共享数据结构要加锁，收益被锁竞争吃掉，破坏核心优势

**横向（对比层）**：
Redis（单线程执行命令 + 丰富数据结构 + 内存）vs Memcached（多线程执行+锁 + 纯 KV 结构 + 内存）：Redis 用单线程换无锁+结构友好，Memcached 用多线程换纯 KV 极限吞吐；Redis vs MySQL：内存 vs 磁盘、单线程无锁 vs 多线程带锁、KV 简单查询 vs 关系型复杂查询，定位互补非替代（经典 Redis 缓存 + MySQL 存储）

**延伸路径**：
- 路径1：Redis 快 -> IO 多路复用 -> epoll -> Reactor 模式 -> Netty/Nginx/Java NIO（同源高并发框架）
- 路径2：单线程快 -> 锁竞争/上下文切换 -> 并发本质问题 -> synchronized 锁升级/AQS/虚拟线程
- 路径3：内存快 -> 内存易失 -> 持久化矛盾（RDB/AOF）-> 缓存一致性/击穿穿透雪崩
- 路径4：专用数据结构 -> 对比 Java 集合（跳表 vs 红黑树、SDS vs C 字符串、ziplist 紧凑存储思想）

## 网络

### TCP 三次握手

**向下（原理层）**：
三次握手 -> SYN/SYN-ACK/ACK 报文 -> 状态机（LISTEN/SYN_RCVD/ESTABLISHED）-> 为什么不是两次（防止历史重复连接）-> 半连接队列（SYN 队列）+ 全连接队列（accept 队列）

**向上（演进层）**：
TCP（面向连接、可靠）-> SYN Flood 攻击（半连接队列耗尽）-> SYN Cookie（不分配资源直接响应）

**横向（对比层）**：
TCP（三次握手、可靠、有序）vs UDP（无连接、不可靠、快）-> QUIC（UDP 之上的可靠传输，HTTP/3 用）

### HTTPS

**向下（原理层）**：
HTTPS -> TLS 握手（非对称加密协商对称密钥）-> 证书链（CA 签名验证）-> 对称加密传输（AES）-> 为什么非对称只握手不用来传数据（慢）

**向上（演进层）**：
HTTP（明文）-> HTTPS（TLS）-> HTTP/2（多路复用，基于 TLS）-> HTTP/3（QUIC，基于 UDP）

**横向（对比层）**：
对称加密（快但密钥分发难）vs 非对称加密（慢但解决密钥分发）-> HTTPS 各用所长
